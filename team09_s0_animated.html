Resource-aware cloud task management

A small cluster of virtual workers needs one coordinated way to match task requirements to live capacity, dispatch work, and retain the results needed to understand performance.

4 CSE enginesTeam 09 · Section BEvidence-led problem framing

The problem and need

Tasks differ in resource demand; worker nodes differ in capacity and current load. When selection, execution, communication and record-keeping happen as separate steps, users and operators cannot reliably see whether work was assigned to a suitable worker or how the run performed.

Problem statement
Efficiently allocating and managing incoming computational tasks across heterogeneous virtual machines is challenging because task resource requirements, VM capacity, current workload and expected completion time must be considered together, while execution status and resource utilization need to be tracked consistently.

People affected

Primary

Workload user

Needs a simple task submission path, reliable completion, clear status and access to results.

Primary

Resource administrator

Needs worker availability, capacity, workload and allocation visibility in one place.

Project team

System developer

Needs clear module interfaces and repeatable inputs to integrate and maintain E1–E4.

Secondary

Analyst / reviewer

Needs persistent execution and resource metrics to compare allocation choices.

Current workflow and pain points

The baseline process is often manual or split across tools. The sequence below records the AS-IS understanding in the S0 document; it is not the proposed CloudCluster workflow.

1

Submit task

Provide a workload and its CPU/RAM needs.

2

Check nodes

Inspect virtual-machine capacity and availability.

3

Choose worker

Apply a basic, static or manual selection rule.

4

Execute & return

Transfer work, collect result and status.

5

Review logs

Find resource and performance data across records.

Uneven utilization

Static choices may miss current load and task suitability.

Fragmented execution

Allocation, dispatch, execution and status may not be coordinated.

Weak comparison

Scattered records make historical analysis difficult.

Scope, feasibility and risks

Semester boundary

  • Submit and validate computational tasks through the React interface and FastAPI controller.
  • Represent worker health and resource telemetry; select among eligible nodes using First Fit, Min-Min or Max-Min.
  • Dispatch to Docker workers, track status and results, and persist task records with SQLAlchemy and SQLite.
  • Measure execution time and CPU/RAM usage for comparison. The supplied architecture marks worker-local queues as planned.

Outside the current boundary: paid public-cloud deployment, multi-datacenter orchestration, Kubernetes, billing and physical partitioning of the host laptop’s RAM.

Feasibility and mitigation

  • Technical: Python, FastAPI, React, Docker and SQLite are available for local development.
  • Resource pressure: start with a small worker set, bound workloads and monitor host/worker use.
  • Scheduling errors: compare fixed workloads with hand-calculated expected eligible-node choices.
  • Worker/API failures: use health state, explicit errors and recorded failed-task status.
  • Scope drift: keep planned queue policies separate from features already shown as implemented.
