Requirements that map to four engines

CloudCluster coordinates task intake, resource checks, scheduling, worker dispatch and result persistence through a FastAPI controller. The cards below describe requirements and acceptance checks; they do not claim that every check has already passed.

Functional requirements

These IDs are a Team 09 traceability set built from the Sprint 1 handbook and the supplied CloudCluster architecture diagram.

FR-01 · E4

Submit and validate a task

The user can select a supported task type and input file through the React interface; FastAPI validates the request and records a task.

Acceptance: valid input returns a task ID and initial status; unsupported type or extension returns HTTP 400.
FR-02 · E1

Monitor worker health

The resource monitor polls worker GET /health and records online/offline status, CPU/RAM use, available RAM and core count.

Acceptance: a worker health response updates node inventory; an unavailable worker is shown offline.
FR-03 · E1

Maintain node inventory

The controller receives configured worker capacity and role information, including primary/backup status.

Acceptance: inventory exposes the latest capacity, role and health state to the scheduler.
FR-04 · E2

Choose an eligible worker

The scheduler applies First Fit, Min-Min or Max-Min using task type, input size, worker eligibility, estimated execution time and active task records.

Acceptance: the assigned worker satisfies task capability/resource checks and the chosen algorithm is recorded.
FR-05 · E3

Dispatch and collect execution

The dispatcher posts task details to the selected worker’s POST /execute endpoint and receives output, metrics or an error.

Acceptance: a worker result updates task state; timeout or execution error is recorded as a failure.
FR-06 · E4

Persist task history

Task, user/session and execution records are persisted through SQLAlchemy in SQLite. Worker containers do not access the database directly.

Acceptance: a completed task remains retrievable from the controller after the UI is refreshed.
FR-07 · E4

Show status and artifacts

The user can retrieve task status, assigned node, timestamps, execution metrics, output artifact or error message.

Acceptance: GET /tasks/{task_id} returns the record or HTTP 404 for an unknown ID.
FR-08 · E2 / E3 / E4

Record measurable outcomes

Capture execution time and available average/peak CPU and RAM metrics so allocation approaches can be compared on the same workloads.

Acceptance: each completed task has its algorithm, worker and returned metrics recorded; no algorithm is declared best without results.

Non-functional requirements

NFR-01 · Reliability

Explicit worker failures

Health-check and execution failures must leave a visible state and error path.

Check: take one worker offline and confirm the inventory and task response explain the outcome.
NFR-02 · Data integrity

One controller-owned record

Controller modules write task state through the persistence layer; workers return data and do not write SQLite.

Check: verify one task ID connects submission, assignment, execution result and history.
NFR-03 · Security

Protect account and task data

Registration/login uses stored password hashes and unique account identifiers. The handbook notes task endpoints do not yet enforce per-user authorization.

Open gap: add and verify per-user task authorization before treating task history as private.
NFR-04 · Performance evidence

Measure before optimizing

Use a fixed workload set and record timing/resource metrics; no numeric latency target or winner is supplied yet.

Check: report observed metrics with workload and algorithm context.
NFR-05 · Maintainability

Keep engine boundaries clear

E1 monitors, E2 schedules, E3 dispatches and E4 handles API/data/UI. These are internal Python modules in one FastAPI application.

Check: each module follows the documented inputs/outputs and avoids duplicate responsibilities.
NFR-06 · Resource bounds

Operate within the student environment

Docker workers share host CPU and memory; tests should use bounded worker counts and workloads.

Check: record host/worker use during trials and avoid claiming physical RAM isolation.

User stories and acceptance

US-01 · Submit a task

As a workload user, I want to submit a supported task file so the controller can validate it and give me a trackable task ID.

Given a supported type and extension, when I submit, then a task record and initial state are returned. Invalid input returns HTTP 400.
US-02 · Find a capable worker

As a resource operator, I want to see current worker health and assignment decisions so tasks are not sent to offline or incompatible nodes.

Given a current worker inventory, when scheduling runs, then the selected node is eligible and the algorithm is recorded.
US-03 · Follow execution

As a workload user, I want to check task state and retrieve the output or error without contacting a worker directly.

Given a task ID, when I retrieve it, then status, assigned node and available result/metrics are returned; an unknown ID returns 404.
US-04 · Compare scheduling choices

As an analyst, I want algorithm, execution time and resource metrics recorded so I can compare First Fit, Min-Min and Max-Min on the same workloads.

Given completed runs, when I review history, then each run has enough context to compare; the system does not assert a winner before measurement.
